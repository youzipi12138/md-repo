**OAuth 提供商（OAuth Provider）** 指的是实现了 OAuth 协议、负责发放访问令牌（Access Token）的一方，也常被称为 **授权服务器（Authorization Server）** 或 **身份提供商（Identity Provider，IdP）**。

### 简单理解

OAuth 是一个开放授权标准，让用户可以在不把账号密码直接告诉第三方应用的情况下，授权第三方应用访问自己的部分数据。

在这个过程中有三个主要角色：

1. **资源所有者（Resource Owner）**：用户本人。
2. **客户端（Client）**：想要访问用户数据的第三方应用（比如某个网站或 App）。
3. **OAuth 提供商 / 授权服务器**：真正持有用户账号、负责验证身份并签发令牌的一方。

**OAuth 提供商就是那个“发通行证”的人。**

### 常见例子

- Google（用 Google 账号登录其他网站）
- GitHub
- Facebook / Meta
- Microsoft（Azure AD / Microsoft Account）
- Apple
- 微信、支付宝、QQ 等国内平台
- 企业自己搭建的 Keycloak、Auth0、Okta、IdentityServer 等

当你看到某个网站写着「使用 Google 登录」「使用 GitHub 登录」时，Google 或 GitHub 就是这个场景下的 **OAuth 提供商**。

### 它具体做什么？

1. 验证用户身份（登录）。
2. 询问用户是否同意授权（Consent）。
3. 向第三方应用发放 **Access Token**（有时还有 Refresh Token、ID Token）。
4. 第三方应用拿着这个令牌去访问用户的受保护资源（比如邮箱、头像、仓库等）。

### 和相关概念的区别

| 概念                 | 含义                                        |
| ------------------ | ----------------------------------------- |
| **OAuth 提供商**      | 发放令牌的一方（授权服务器）                            |
| **OAuth 客户端**      | 申请令牌的第三方应用                                |
| **资源服务器**          | 真正存放用户数据的服务器（有时和提供商是同一家）                  |
| **OpenID Connect** | 在 OAuth 基础上增加了身份认证（登录）能力，很多 OAuth 提供商同时支持 |





### 1. 验证用户身份（登录）

当用户在第三方应用（比如某个网站）点击「使用 Google 登录」时：

1. 第三方应用把用户重定向到 **OAuth 提供商**（Google）的登录页面。
2. 用户在 Google 的页面上输入账号密码（或者已经登录过，就直接跳过）。
3. Google 验证用户身份成功后，会记住“这个用户已经认证过了”。

**关键点**：  
密码只在 OAuth 提供商自己的页面输入，第三方应用**永远看不到**用户的密码。这是 OAuth 最核心的安全设计之一。

---

### 2. 询问用户是否同意授权（Consent / 同意授权）

身份验证通过后，OAuth 提供商会弹出一个**授权确认页面**，上面会写清楚：

- 哪个应用在请求权限
- 它想要访问你的哪些信息（比如：查看邮箱、读取头像、访问仓库……）
- 权限范围（Scope）

用户可以：

- 同意 → 继续流程
- 拒绝 → 流程中断，回到第三方应用并提示失败

这一步叫 **Consent（用户同意）**。  
它确保用户清楚知道自己把什么权限给了谁，而不是被偷偷授权。

---

### 3. 向第三方应用发放令牌

用户点了「同意」之后，OAuth 提供商会通过一系列安全步骤，最终把令牌发给第三方应用。常见的令牌有三种：

|令牌|作用说明|
|---|---|
|**Access Token**|最核心的令牌。第三方应用拿它去访问用户的受保护资源。有效期通常较短（几分钟到几小时）。|
|**Refresh Token**|用来在 Access Token 过期后，安静地换取新的 Access Token，而不需要用户重新登录。有效期较长。|
|**ID Token**|主要出现在 OpenID Connect（OAuth 的扩展）中，用来告诉第三方应用“用户是谁”（包含用户基本信息，比如 sub、email、name）。|

**发放过程（简化版）**：

1. OAuth 提供商先给第三方应用一个临时的 **Authorization Code（授权码）**（通过浏览器重定向）。
2. 第三方应用的后端再用这个授权码 + 自己的 Client Secret，向 OAuth 提供商换取真正的 Access Token（和可能的 Refresh Token、ID Token）。

用授权码换令牌这一步是在**服务器之间**完成的，浏览器不参与，这样更安全。

---

### 4. 第三方应用拿着令牌去访问用户的资源

拿到 Access Token 之后，第三方应用就可以用它去调用 OAuth 提供商的 **API** 了。

例如：

- 用 Google 的 Access Token 去调用 Google People API 获取用户头像和邮箱
- 用 GitHub 的 Access Token 去读取用户的仓库列表
- 用微信的 Access Token 去获取用户的 openid 和昵称

调用时通常会在请求头里带上：

http

```
Authorization: Bearer <Access Token>
```

OAuth 提供商（或它的资源服务器）收到请求后会验证这个 Token 是否有效、是否有对应权限，然后返回数据。

---

### 整体流程一句话总结

> 用户 → 在 OAuth 提供商那里登录并同意授权 → OAuth 提供商发给第三方应用一个临时通行证（Access Token）→ 第三方应用拿着通行证去访问用户的数据。

整个过程中，第三方应用**既拿不到用户密码，也拿不到长期有效的凭证**（除非有 Refresh Token，而且 Refresh Token 通常也被严格保护）。
