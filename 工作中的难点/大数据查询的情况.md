# SDK 后端服务假死故障分析与优化方案

## 一、故障结论

**当前问题不是普通的接口响应慢，而是后端 JVM 发生 OOM，导致 Tomcat Poller 线程死亡，HTTP 服务进入假死状态。**

同时，多个应用实例重复执行全量 ETL 任务，导致 PostgreSQL I/O 压力过大、长事务锁等待，两者叠加造成系统整体不可用。

### 1.1 故障表现

|检查项|实际结果|说明|
|---|---|---|
|`/sdk-api/v1/signal/market?days=30`|15015ms，响应体 0 字节|触发前端 15 秒超时|
|curl 直连|60 秒后 Nginx 504|后端没有正常响应|
|industry/tree|请求挂起|非单个接口问题|
|brand/1|请求挂起|多个业务接口不可用|
|actuator/health|请求挂起|健康检查也无法正常响应|

### 1.2 核心原因

1. JVM 堆内存不足，发生 `OutOfMemoryError`。
    
2. Tomcat Poller 线程因 OOM 死亡，无法正常处理新连接的读写事件。
    
3. PostgreSQL 同时承受多个实例的全量重建任务，产生大量 I/O 等待和锁竞争。
    
4. Dev 环境直接连接生产数据库，并且定时任务没有进行实例隔离。

## 二、故障现场分析

### 2.1 JVM OOM 导致 Tomcat 假死

故障机器：ai14

后端进程：PID 905613

关键日志：

```
16:41:41 INFO
MarketSignalController.brandRanking
java.lang.OutOfMemoryError: Java heap space

16:41:41 ERROR
Handler dispatch failed:
java.lang.OutOfMemoryError: Java heap space

Exception in thread "http-nio-18160-Poller"
java.lang.OutOfMemoryError: Java heap space
```

### 2.2 Tomcat 为什么会假死？

Tomcat NIO 模型中，主要有三个关键角色：

|组件|职责|
|---|---|
|Acceptor|接收客户端 TCP 连接|
|Poller|监听 Socket 的读写事件，派发 I/O 任务|
|Executor|执行实际的 HTTP 请求处理任务|

正常请求流程：

```
客户端发起请求
      |
      v
  Acceptor
      |
      v
   Poller
      |
      v
  Executor
      |
      v
 Controller
      |
      v
  Service
      |
      v
  Database
```

本次故障中，Poller 线程因 OOM 死亡：

```
客户端发起请求
      |
      v
  Acceptor（正常）
      |
      v
  Poller（已死亡）
      |
      X
  无法正常派发 I/O 事件
      |
      v
客户端持续等待，最终超时
```

因此出现了一个非常典型的现象：

- TCP 连接可以建立。
    
- curl 不会立即报 Connection Refused。
    
- HTTP 请求一直等待。
    
- Tomcat 工作线程处于 WAITING 状态。
    
- 健康检查接口也无法正常响应。
    
- JVM 进程仍然存在，进程监控可能误判为正常。
    

**关键结论：进程存活不代表 HTTP 服务健康。**

### 2.3 现场线程与 Socket 检查

|检查项|结果|说明|
|---|---|---|
|jstack 中 Poller|0 个|Poller 线程已经死亡|
|CLOSE_WAIT Socket|178 条|存在大量未正常处理的连接|
|http-nio-18160-exec-*|全部 WAITING|工作线程没有收到正常派发的任务|
|Acceptor|RUNNABLE|TCP 接收线程仍然正常|
|scheduling-1|仍在执行 SQL|JVM 部分后台任务仍然运行|

## 三、JVM 内存问题分析

### 3.1 JVM 配置不合理

当前启动命令：

```
java -Xms1g -Xmx2g \
  -jar /www/wwwroot/cicd/sdk-java-dev/sdk-java.jar \
  --spring.profiles.active=dev \
  --server.port=18160
```

当前机器资源：

- 物理内存：460GB
    
- CPU：56 核
    
- JVM 最大堆：2GB
    

对于当前数据规模和应用负载，2GB 堆内存明显偏小。

但需要注意：不能仅仅通过扩大堆内存解决问题，必须同时治理内存中的大对象和重复数据加载。

### 3.2 Heap Dump 对象分析

|对象类型|实例数量/占用|说明|
|---|---|---|
|BrandIndustryDO|701,661 个|行业树、主路径快照|
|SearchPoolEntry|233,887 个|探索洞察检索池，远超约 4.7k 行的预期|
|MyBatis PropertyTokenizer / MetaObject / BeanWrapper|60 万+|大结果集反射映射产生的对象|
|byte[]|720 万个 / 320MB|日志、SQL、响应缓冲等|
|FillerElement|141MB|G1 堆内存紧张时的填充对象，说明堆压力严重|

### 3.3 核心内存问题：请求重复加载全量数据

`MarketSignalServiceImpl.query()` 每次请求都会执行多组全量查询：

|查询方法|返回行数|
|---|---|
|selectAllStats()|23,592|
|selectAllPlatformStats()|29,195|
|selectSpuStats()|27,863|
|selectRangeTotals()|18,837|
|selectBrandLogos()|约 23,000 个 ID|
|selectDailyForBrands()|大量品牌日数据|
|selectSeries()|趋势数据|

这意味着：

1. 每次请求都从数据库读取大量数据。
    
2. MyBatis 将结果集映射成 Java 对象。
    
3. 大量对象进入 JVM 堆内存。
    
4. 并发请求进一步放大内存占用。
    
5. GC 压力不断增加，最终出现 OOM。
    

**本质问题：将全量数据加载到 JVM 内存中，再由 Java 完成筛选和聚合，缺少合理的数据访问边界。**

## 四、Dev 环境配置问题

当前后端使用：

```
--spring.profiles.active=dev
```

但 Dev 环境直接连接生产 SDK 数据库。

存在以下风险：

|问题|风险|
|---|---|
|Dev 直接连接生产数据库|开发任务可能影响生产业务|
|API Key 鉴权关闭|接口存在未授权访问风险|
|所有同步任务开启|多个实例可能重复执行 ETL|
|DEBUG 日志开启|日志量过大，增加磁盘 I/O|
|数据库密码明文配置|数据库凭证泄露风险|

另外，2 小时内 `com.mibads.sdk` 相关日志达到 122MB。

### 优化方向

- Dev、Test、Prod 环境必须隔离。
    
- Dev 环境禁止直接执行生产 ETL。
    
- 生产环境必须开启 API Key 鉴权。
    
- DEBUG 日志仅在必要时短期开启。
    
- 数据库密码通过环境变量或密钥管理服务注入。
    
- 定时任务增加独立开关。

## 五、PostgreSQL 数据库问题分析

### 5.1 数据库本身不是唯一瓶颈

健康状态下实测两个核心 SQL：

|SQL|执行耗时|
|---|---|
|selectRangeTotals（30 天）|188ms|
|selectSeries（30 天）|139ms|

这说明核心 SQL 在数据库正常状态下并不慢。

真正的问题是：**多个实例同时执行全量数据重建，造成 PostgreSQL I/O 竞争和事务锁等待。**

### 5.2 多实例重复执行 ETL

现场发现多个客户端同时执行全量重建：

|来源 IP|当前执行任务|
|---|---|
|120.244.85.64|开发机执行全量重建|
|120.244.85.90|开发机执行全量重建|
|172.21.2.62|ai14 内网实例执行全量重建|

典型 SQL：

```
SELECT DISTINCT sb.brand_id ...

INSERT INTO signal_src ...

DELETE FROM public.brand_signal_daily;
```

其中：

- SELECT DISTINCT：执行时间最长达到 564 秒。
    
- INSERT：存在持续写入压力。
    
- DELETE：等待 transactionid 锁，最长达到 168 秒。
    

### 5.3 为什么会重复执行？

代码中存在多个定时任务：

|任务|定时频率|
|---|---|
|MarketSignalServiceImpl|每 6 小时|
|BrandRankingServiceImpl|每 6 小时|
|BrandCommercialStatServiceImpl|每 30 分钟|
|SpuTopicStatService|每天|

问题在于：

- 每个应用实例启动后都会执行定时任务。
    
- 没有分布式锁。
    
- 没有区分 Web 实例与 ETL 实例。
    
- Dev 环境也会执行生产数据重建。
    

最终导致多个实例重复扫描、计算和写入相同数据。

### 5.4 数据库其他风险

|检查项|当前情况|风险|
|---|---|---|
|statement_timeout|0（永不超时）|SQL 可能无限执行|
|xiaohongshu_video 死元组|2478 万|表膨胀、I/O 压力|
|客户端 IO 等待累计|1,365,870 秒|数据库存在明显 I/O 等待|

## 六、解决方案

按照紧急程度划分为 P0、P1、P2。

## 6.1 P0：立即恢复服务

目标：先恢复 HTTP 服务，阻止继续产生资源竞争。

### 1. 重启后端服务

先停止已经假死的 JVM，再按照合理的内存配置重新启动。

```
kill 905613
```

注意：重启前确认进程、服务管理方式和启动参数，避免误杀其他实例。

### 2. 取消重复执行的 ETL 任务

对于正在执行的开发机重建任务，确认任务来源和影响后，使用：

```
SELECT pg_cancel_backend(pid);
```

注意：

- `pg_cancel_backend` 取消当前 SQL。
    
- 不等于永久停止定时任务。
    
- 如果任务由应用定时器触发，下一轮仍然可能重新执行。
    

### 3. 关闭 Dev 环境生产定时任务

建议增加统一配置：

```
app:
  scheduler:
    enabled: false
```

通过 `@ConditionalOnProperty` 控制定时任务 Bean 是否创建。

```
@Component
@ConditionalOnProperty(
    prefix = "app.scheduler",
    name = "enabled",
    havingValue = "true"
)
public class MarketSignalScheduler {
    // 定时任务
}
```

Dev 环境关闭生产数据重建任务，生产 ETL 只允许指定实例执行。

## 6.2 P1：根治多实例重复 ETL

目标：从架构层面解决重复计算、数据库锁竞争和资源争抢。

### 1. 引入分布式锁

推荐使用 ShedLock 或 PostgreSQL Advisory Lock。

ShedLock 示例：

```
@SchedulerLock(
    name = "marketSignalRebuild",
    lockAtMostFor = "PT2H"
)
@Scheduled(
    fixedDelay = 6 * 60 * 60_000L,
    initialDelay = 3 * 60_000L
)
public void scheduledRebuild() {
    // 执行全量数据重建
}
```

效果：

- 多个实例同时启动时，只允许一个实例获取锁。
    
- 避免相同任务重复执行。
    
- 防止多个实例同时重建同一张表。
    

注意：合理设置锁的持有时间和续期策略，避免任务执行超过锁有效期后出现并发重建。

### 2. ETL 与 Web 服务进程隔离

推荐架构：

```
             用户请求
                |
                v
          Nginx / Gateway
                |
                v
          Web 服务 JVM
                |
                v
            PostgreSQL


          ETL 独立进程
                |
                v
          全量数据重建
                |
                v
            PostgreSQL
```

具体方案：

- Web JVM：只负责接口查询、业务逻辑和轻量计算。
    
- ETL JVM：专门负责数据扫描、清洗、聚合和重建。
    
- ETL 使用独立配置和连接池。
    
- ETL 由单实例调度，避免多个节点重复执行。
    

### 3. 改造全量 DELETE + INSERT

当前模式：

```
DELETE FROM brand_signal_daily;

INSERT INTO brand_signal_daily
SELECT ...;
```

存在的问题：

- DELETE 产生大量死元组。
    
- 长事务占用资源。
    
- 并发重建容易产生锁等待。
    
- 数据重建过程中可能影响查询。
    

推荐改为影子表模式：

```
brand_signal_daily
        |
        | 线上查询
        v
     正式表


ETL 重建
    |
    v
brand_signal_daily_new
    |
    | 数据构建完成
    v
校验数据完整性
    |
    v
原子切换
    |
    v
正式表使用新数据
```

优势：

- 重建过程不影响线上查询。
    
- 避免正式表长时间处于清空状态。
    
- 降低 DELETE 带来的死元组问题。
    
- 可以在切换前进行数据校验。
    

注意：PostgreSQL 表切换需要处理事务、锁、索引、约束、权限以及并发查询问题，不能简单地认为两条 RENAME 就能完成所有安全切换。

### 4. 设置数据库 SQL 超时

当前：

```
statement_timeout = 0
```

意味着 SQL 默认没有执行时间限制。

建议按业务类型区分：

|场景|建议超时时间|
|---|---|
|Web 查询|20 秒|
|ETL 重建|30 分钟|

连接池配置示意：

```
# Web 数据库连接
connection-init-sql: SET statement_timeout='20s'
```

ETL 使用独立连接池：

```
SET statement_timeout = '30min';
```

避免异常 SQL 长时间占用数据库资源。

### 5. 优化 PostgreSQL 索引

针对高频查询增加覆盖索引。

```
-- 趋势查询
CREATE INDEX idx_signal_daily_date
ON brand_signal_daily (stat_date)
INCLUDE (content_cnt, creator_cnt);


-- 品牌区间统计
CREATE INDEX idx_signal_daily_date_brand_platform
ON brand_signal_daily (stat_date, brand_id, platform)
INCLUDE (content_cnt, creator_cnt);


-- 品牌排行榜和趋势
CREATE INDEX idx_delivery_fact_date_brand
ON brand_delivery_fact (stat_date, brand_id)
INCLUDE (platform, play_cnt, interaction_cnt, price);
```

优化目标：

- 减少回表操作。
    
- 提高 Index Only Scan 的使用机会。
    
- 降低大范围统计查询的 I/O 成本。
    

注意：覆盖索引是否生效取决于查询条件、数据分布、可见性映射等因素，需要结合 `EXPLAIN (ANALYZE, BUFFERS)` 验证。

## 6.3 P2：优化 API 与前端数据契约

目标：避免接口一次性返回全量数据，降低数据库和 JVM 的内存压力。

### 当前问题

```
GET /v1/signal/market
```

一次性返回全部品牌快照数据，但前端实际上只展示 10 行。

存在的问题：

- 后端读取全量数据。
    
- MyBatis 映射大量对象。
    
- JVM 保存大量临时数据。
    
- 网络传输大量无用字段。
    
- 前端只使用其中一小部分数据。
    

### 推荐改造

使用服务端分页：

```
GET /v1/signal/market?page=1&size=10&days=30
```

返回：

```
{
  "code": 0,
  "data": {
    "total": 10000,
    "page": 1,
    "size": 10,
    "records": []
  }
}
```

核心优化：

1. 使用 SQL LIMIT / OFFSET 或基于游标的分页。
    
2. 将筛选、排序和聚合尽可能下推到 PostgreSQL。
    
3. 只返回页面需要的字段。
    
4. 高频统计结果采用快照缓存。
    
5. 趋势数据与品牌列表拆分接口，按需加载。

## 七、未来技术架构演进

根据数据规模、实时性和分析需求，选择不同的技术方案。

|业务需求|推荐技术方案|
|---|---|
|分钟级、秒级信号，新内容进入后快速更新|Kafka + Flink|
|数据达到几十亿行，需要跨源 Join 和机器学习|Iceberg / Hudi + Spark|
|BI 任意维度秒级分析，几百个并发|ClickHouse / Doris|
|只是将 ETL 从 PostgreSQL 中移出，数据规模暂时不大|DuckDB / Polars|

### 7.1 Kafka + Flink：实时数据处理

适用场景：

- 抖音、小红书新视频进入。
    
- 新增达人内容需要快速识别。
    
- 商单识别结果需要实时更新。
    
- 品牌商业信号需要分钟级刷新。
    

架构：

```
视频平台数据采集
        |
        v
      Kafka
        |
        v
      Flink
        |
        v
  实时清洗 / 聚合 / 商单识别
        |
        v
 PostgreSQL / ClickHouse
        |
        v
       API
        |
        v
       前端
```

### 7.2 Lakehouse + Spark：大规模离线计算

适用场景：

- 达人历史作品数据规模持续增长。
    
- 多平台数据关联分析。
    
- 跨数据源 Join。
    
- 长周期商业趋势分析。
    
- 大规模机器学习特征计算。
    

架构：

```
数据采集
   |
   v
  ODS 原始数据层
   |
   v
Lakehouse（Iceberg / Hudi）
   |
   v
Spark 批处理
   |
   v
清洗 / 转换 / 聚合
   |
   v
DWD / DWS / ADS
   |
   v
ClickHouse / PostgreSQL
   |
   v
业务 API / BI
```

### 7.3 ClickHouse / Doris：OLAP 查询服务

适用场景：

- 大规模品牌排行榜。
    
- 多维度达人分析。
    
- 跨平台商业趋势统计。
    
- BI 报表。
    
- 高并发聚合查询。
    

建议职责划分：

|数据库|主要职责|
|---|---|
|PostgreSQL|业务主数据、事务处理、业务查询|
|ClickHouse / Doris|大规模分析、聚合、报表|
|Lakehouse|原始数据、历史数据、离线计算|

## 八、推荐实施路线

不建议当前阶段直接引入 Spark、Flink、ClickHouse 等一整套复杂架构。

应该先解决现有系统的资源管理和任务调度问题。

### 第一阶段：恢复与稳定（现在）

- 重启 JVM，恢复 HTTP 服务。
    
- 合理调整 JVM 堆内存。
    
- 停止重复执行的 ETL。
    
- Dev 环境关闭生产定时任务。
    
- Web 和 ETL 任务进行隔离。
    
- 为数据库连接设置 SQL 超时。
    
- 检查 JVM Heap Dump 和 GC 日志。
    

### 第二阶段：架构治理（本周）

- 引入 ShedLock 或 PostgreSQL Advisory Lock。
    
- 将 ETL 独立成单实例进程。
    
- 将 DELETE + INSERT 改造成影子表切换。
    
- 优化 PostgreSQL 索引。
    
- 对大结果集进行分页和分批处理。
    
- 将全量数据加载改为按需查询。
    
- 增加快照缓存。
    

### 第三阶段：性能优化（后续）

- 优化 API 数据返回结构。
    
- 前端改为服务端分页。
    
- 品牌列表、趋势图、统计指标拆分加载。
    
- 使用 EXPLAIN ANALYZE 持续分析 SQL。
    
- 增加 JVM、GC、连接池和数据库监控。
    
- 建立 ETL 执行状态和失败告警机制。
    

### 第四阶段：数据架构升级（业务增长后）

- 实时计算：Kafka + Flink。
    
- 离线计算：Lakehouse + Spark。
    
- 大规模 OLAP：ClickHouse / Doris。
    
- 根据实际业务规模逐步拆分数据存储与计算职责。

## 十、核心总结

本次故障并不是单纯的 SQL 性能问题，而是 JVM 内存管理、Tomcat 线程模型、数据库任务调度和环境隔离共同造成的系统性故障。

需要重点解决四个问题：

1. **应用层：** JVM OOM 导致 Tomcat Poller 死亡，必须建立真正的 HTTP 健康检查和 JVM 资源监控。
    
2. **数据层：** 每次请求加载大量全量数据，需要分页、按需查询和快照缓存。
    
3. **任务层：** 多个实例重复执行全量 ETL，必须引入分布式锁和独立 ETL 进程。
    
4. **架构层：** PostgreSQL 不应该同时承担所有业务查询、全量重建和大规模分析任务。
    

**最终原则：Web 负责查询，ETL 负责计算，数据库负责存储与查询优化，实时计算和离线计算根据业务需求逐步拆分。**

先治理现有架构，再考虑引入新的大数据技术。不要用增加技术组件的方式掩盖现有系统的设计问题。
