# **二、上下文窗口（Context Window）是什么？**

现在理解了 Token，再来理解上下文窗口就容易了。

**上下文窗口就是模型单次处理任务时，能够容纳的最大 Token 数量。**

你可以把它理解为模型的一块临时工作区。

比如：

假设某个模型支持 128K 上下文窗口。

那么它一次请求能够处理的上下文 Token 总量上限就是 128K。

这里的 K 通常表示 1024。

\[ 128K = 128 \times 1024 = 131072 \]

也就是 131072 个 Token。

## **1. 用计算机内存理解上下文窗口**

可以把上下文窗口理解成计算机的内存。

|计算机|大模型|
|---|---|
|内存容量|上下文窗口|
|数据|Token|
|程序运行时读取的数据|模型当前处理的上下文|
|内存不足|Context Length Exceeded|

举个例子：

你正在和 Agent 对话。

第一轮：

> 帮我找 10 个适合 AI 产品投放的抖音达人。

第二轮：

> 粉丝量要求 50 万以上。

第三轮：

> 只要女性达人。

第四轮：

> 再筛选一下，要求近 30 天互动率超过 5%。

第五轮：

> 把这些达人按照商业价值排序。

这些对话都可能成为模型后续请求的上下文。

模型需要结合前面说过的条件，才能正确理解第五轮的意思。

因此，随着对话变长，上下文可能不断增加。

## **2. 上下文窗口里面到底装了什么？**

这是一个非常重要的问题。

很多人以为上下文窗口只装用户发送的消息。

实际上远不止如此。

一次典型的 Agent 请求，可能包含：

**一次模型请求的上下文组成**

**System Prompt**

规则和角色

定义 Agent 身份、行为规范、约束条件

**历史对话**

历史消息

用户和助手之前说过的内容

**工具定义**

Function Calling

工具名称、描述、参数 Schema

**RAG 检索内容**

外部知识

向量数据库检索出来的文档、业务数据

**当前用户问题**

本轮输入

用户这次真正提出的问题

**模型生成内容**

输出预算

模型接下来可能生成的 Token

示意图：实际请求的组织方式取决于模型和 API；各部分都可能占用上下文预算。

特别注意：

**工具定义也可能消耗 Token！**

例如你的 Agent 注册了 50 个工具：

```
{
  "name": "search_influencers",
  "description": "根据行业、平台、粉丝量等条件搜索达人",
  "parameters": {
    "type": "object",
    "properties": {
      "platform": {
        "type": "string"
      },
      "industry": {
        "type": "string"
      },
      "follower_min": {
        "type": "integer"
      }
    }
  }
}
```

这些工具定义需要传递给模型，模型才能知道自己有哪些工具可以调用。

工具越多、描述越复杂，可能消耗越多 Token。

这也是为什么 Agent 的工具注册中心不能无限堆砌工具。

# **三、上下文窗口和 Token 到底是什么关系？**

这是最核心的关系。

假设某个模型的上下文窗口是 128K。

一次请求中：

|内容|Token 消耗|
|---|---|
|System Prompt|5,000|
|历史对话|20,000|
|工具定义|8,000|
|RAG 检索内容|10,000|
|当前用户问题|1,000|
|模型本轮输出预留|4,000|
|**合计**|**48,000**|

那么：

\[ 131072 - 48000 = 83072 \]

剩余约 83K Token 的上下文预算。

注意，这里是一个简化的预算模型。不同 API 对输入、输出、推理 Token 的统计方式有所区别，但你在工程上应该始终给输出预留空间。

## **1. 不同上下文窗口的区别**

下面是一些常见的上下文规模：

|上下文窗口|Token 数量|直观理解|
|---|---|---|
|8K|8,192|短对话、小任务|
|32K|32,768|中等长度任务|
|128K|131,072|长对话、较长文档|
|200K|204,800|大型文档、复杂 Agent|
|1M|1,048,576|超长上下文任务|

这里的数字是容量示例，不代表所有模型都支持这些规格。

你可能经常看到模型介绍：

- 128K Context
    
- 200K Context
    
- 1M Context
    

它们说的就是上下文窗口容量。

**上下文窗口容量对比**

**8K**

8,192 Tokens

**32K**

32,768 Tokens

**128K**

131,072 Tokens

**200K**

204,800 Tokens

**1M**

1,048,576 Tokens

按 1M 为最大值的线性比例展示。

但是，我想纠正一个容易产生的误区：

**上下文窗口越大，不代表模型就一定越聪明。**

上下文窗口解决的是模型一次能够接收多少信息的问题。

它不直接代表：

- 模型的推理能力。
    
- 模型的知识储备。
    
- 模型的准确率。
    
- 模型能否真正记住所有细节。
    

一个模型支持 1M 上下文，不意味着它能在 1M Token 中准确找到每一条信息。

## **2. 为什么上下文越大，成本可能越高？**

因为模型需要处理更多 Token。

假设某个 API 的价格如下（纯假设，用于演示）：

- 输入：每百万 Token 2 美元。
    
- 输出：每百万 Token 8 美元。
    

那么一次请求：

- 输入 50,000 Token。
    
- 输出 2,000 Token。
    

费用：

\[ 50,000 / 1,000,000 \times 2 \]

\[ + 2,000 / 1,000,000 \times 8 \]

\[ = 0.116 \text{ 美元} \]

如果你的 Agent 有 10 万次这样的请求，成本就会变成 11,600 美元。

实际价格需要以模型供应商的最新定价为准，还要考虑缓存输入、推理 Token 等计费规则。

这就引出了一个重要的工程问题：

**Agent 不能每次都把所有历史对话原封不动地发送给模型。**

这就是为什么要做上下文管理。

# **四、为什么 Agent 对话越长，模型越容易忘记前面的内容？**

这里涉及一个重要的底层技术：Transformer 和 Attention（注意力机制）。

## **1. 模型如何理解上下文？**

假设你告诉模型：

第一轮：

> 我们公司主要做达人营销，服务的行业是 AI、游戏、App 和社交。

第二十轮：

> 帮我找一些适合这个行业的达人。

模型需要知道这里的「这个行业」指的是之前说过的行业。

它就需要根据上下文中的信息，建立不同 Token 之间的关联。

Transformer 中非常重要的机制就是 Self-Attention（自注意力机制）。

简单理解：

**每个 Token 在处理时，可以根据注意力机制关注上下文中与自己相关的其他 Token。**

例如：

**一句话中的关联关系**

我们公司主要做 **达人营销**，主要服务 **AI、游戏、App、社交** 行业。

后续用户提问

帮我找适合 **这个行业** 的达人。

模型通过上下文关联，理解「这个行业」的指代。

不过，Self-Attention 并不意味着模型可以无限读取信息。

模型有上下文窗口限制，而且上下文越长，处理成本和计算复杂度也可能增加。

## **2. 为什么有些模型有 1M 上下文，却仍然会忘记信息？**

这里有一个非常重要的现象：

**Lost in the Middle（中间信息丢失）。**

意思是：在很长的上下文中，模型对某些位置的信息利用能力可能不均衡。

例如：

你给 Agent 发送了 100 页达人数据。

- 第 1 页：某个达人的粉丝量。
    
- 第 50 页：某个达人的真实商业报价。
    
- 第 100 页：用户的筛选要求。
    

即使这些内容都在上下文窗口里，模型也不一定能够准确地综合利用所有信息。

原因包括：

- 注意力分配不均。
    
- 信息之间存在大量干扰。
    
- 上下文中有重复、无关内容。
    
- 关键约束被大量文本淹没。
    
- 模型本身的长上下文检索和推理能力有限。
    

因此，实际工程中不能只依赖扩大上下文窗口。

还需要：

- RAG 检索。
    
- 结构化数据查询。
    
- 历史对话摘要。
    
- 关键约束保留。
    
- 分阶段任务执行。
