大模型本身通常没有真正的长期记忆。所谓的记忆能力，主要是由上下文窗口（Context Window）、对话历史存储、记忆提取、向量检索和 Prompt 组装等机制共同实现的。


我们从底层原理开始拆解。
# **一、先理解：大模型本身其实是没有记忆的**

假设你今天和一个大模型说：

```
你：我现在在做一个达人推荐 Agent。
你：我们公司主要做抖音和小红书达人营销。
你：后端使用 Java，数据库使用 MySQL。
```

模型收到这些信息后，生成回答。

第二天，你重新开启一个完全独立的请求：

```
你：我昨天在做什么项目？
```

如果这次请求没有携带之前的对话内容，模型通常是不知道的。

为什么？

因为大模型的核心工作机制是：

1. 接收输入 Token。
    
2. 通过 Transformer 计算 Token 之间的关系。
    
3. 根据上下文预测下一个 Token。
    
4. 不断生成后续 Token。
    

模型参数中存储的是训练过程中学到的知识和模式，而不是实时把你的每句话写入模型参数。

所以：

- 模型参数：长期训练得到的知识。
    
- 上下文窗口：当前请求能够看到的信息。
    
- 外部记忆：系统额外保存的用户历史信息。
 这三个概念必须区分开。

# **二、大模型是如何记住上一次对话的？**

我们先看一个简化的架构。

## **大模型记忆系统架构**

**用户发送消息**

例如：继续讲讲昨天的 Agent 架构

**记忆管理系统（Memory Manager）**

**短期记忆**

当前对话历史、上下文窗口

**长期记忆**

用户画像、历史偏好、重要事实

**历史对话库**

完整对话记录、历史消息

**语义检索**

Embedding、向量搜索、召回

**Prompt 组装**

System Prompt + 记忆 + 历史对话 + 当前问题

**LLM 推理并生成回答**

这里面有四个非常关键的机制。

## **三、第一种记忆：上下文窗口（Context Window）**

这是最基础，也是最重要的一种。

假设你和模型连续聊了三轮：

**第一轮**

历史消息

用户：我正在开发一个达人推荐 Agent。

**第二轮**

历史消息

用户：后端使用 Python，数据来自 MySQL 和 OpenSearch。

**第三轮**

当前消息

用户：那我的 Agent 应该如何设计工具调用？

**实际发送给模型的输入**

**SYSTEM PROMPT**

你是一个专业的技术助手。

**HISTORY**

第一轮：我正在开发一个达人推荐 Agent。

第二轮：后端使用 Python，数据来自 MySQL 和 OpenSearch。

**CURRENT INPUT**

那我的 Agent 应该如何设计工具调用？

注意一个非常重要的细节：

**模型并不是自动记住了前两轮，而是应用程序在第三轮请求时，把前两轮消息重新发送给模型了。**

这就是上下文记忆。

例如，调用大模型 API 时，可能是这样的：

```
{
  "messages": [
    {
      "role": "system",
      "content": "你是一个技术助手"
    },
    {
      "role": "user",
      "content": "我正在开发一个达人推荐 Agent"
    },
    {
      "role": "assistant",
      "content": "明白，我们可以从架构开始"
    },
    {
      "role": "user",
      "content": "后端使用 Python，数据来自 MySQL 和 OpenSearch"
    },
    {
      "role": "assistant",
      "content": "可以设计成分层架构"
    },
    {
      "role": "user",
      "content": "那我的 Agent 应该如何设计工具调用？"
    }
  ]
}
```

这里的 `messages` 就是模型当前能够看到的对话内容。
### **那么上下文窗口有什么限制？**

上下文窗口本质上是模型一次请求能够处理的 Token 容量。

例如，假设某模型的上下文窗口是 128K Token。

你连续聊了几个月，所有对话累计达到了 500K Token。

那么模型不可能在一次请求中直接读取全部 500K Token。

系统必须做一些处理：

- 保留最近的对话。
    
- 删除不重要的历史内容。
    
- 把较早的对话压缩成摘要。
    
- 从历史记录中检索与当前问题有关的内容。
    

这就引出了第二种机制。

## **四、第二种记忆：历史对话数据库**

这部分实际上不是大模型的能力，而是应用后端的能力。

假设你正在开发一个 AI 聊天系统。

后端一般会有类似这样的数据表：

**conversation（会话表）**

|字段|作用|
|---|---|
|id|会话 ID|
|user_id|用户 ID|
|title|会话标题|
|created_at|创建时间|

**message（消息表）**

|字段|作用|
|---|---|
|id|消息 ID|
|conversation_id|所属会话|
|role|user / assistant / tool|
|content|消息内容|
|created_at|消息时间|

例如：

```
conversation_id = 1001

message 1: user
我正在做达人推荐 Agent

message 2: assistant
可以采用 Agent + Tools 架构

message 3: user
我应该如何设计工具注册中心？

message 4: assistant
可以设计 Tool Registry
```

当你第二天重新打开这个会话：

1. 前端传递 conversation_id。
    
2. 后端根据 conversation_id 查询历史消息。
    
3. 后端获取最近 N 条消息。
    
4. 组装成 messages。
    
5. 调用大模型 API。
    

这样模型就能接着昨天的话题聊。

**所以，真正保存聊天记录的通常是数据库，而不是大模型。**

## **五、第三种记忆：长期记忆（Long-term Memory）**

这个才是最有意思的。

假设你今天和模型聊了 100 次，聊过：

- 你正在开发达人推荐 Agent。
    
- 你使用 Java 和 MySQL。
    
- 你对 LangGraph 感兴趣。
    
- 你正在学习 Agent Runtime。
    
- 你希望技术解释足够深入。
    

如果每次对话都把这 100 次聊天全部塞给模型，成本很高，而且非常浪费上下文。

所以需要一个机制：

**从大量对话中提取真正值得长期保存的信息。**

这通常叫 Memory Extraction（记忆提取）。

### **1. 记忆是如何产生的？**

假设你对模型说：

```
我目前在一家达人营销公司工作。

公司每天采集抖音和小红书的数据，
然后通过语义分析进行达人推荐。

我现在负责开发公司的达人推荐 Agent。
```

系统可以让一个模型专门进行信息提取。

例如：

```
你是一个记忆提取器。

请从用户的对话中提取：
1. 长期稳定的个人信息
2. 工作背景
3. 技术栈
4. 长期项目
5. 用户偏好

忽略临时问题和无意义闲聊。

输出结构化 JSON。
```

提取结果可能是：

```
{
  "user_profile": {
    "industry": "达人营销",
    "role": "后端开发",
    "current_project": "达人推荐 Agent",
    "data_platforms": [
      "抖音",
      "小红书"
    ],
    "technologies": [
      "Java",
      "MySQL",
      "OpenSearch",
      "Redis",
      "Kafka"
    ],
    "preferences": [
      "喜欢深入理解底层原理",
      "偏好实际业务案例"
    ]
  }
}
```

然后系统把这些信息保存到长期记忆存储中。

### **2. 长期记忆存在哪里？**

一般有几种选择：

|存储方式|适合保存什么|
|---|---|
|MySQL / PostgreSQL|用户画像、结构化事实|
|Redis|临时状态、会话缓存|
|Elasticsearch / OpenSearch|历史文本检索|
|向量数据库|语义记忆、相似历史对话|
|文件 / JSON|记忆摘要、长期上下文|

这里有一个容易误解的地方：

**长期记忆不等于向量数据库。**

向量数据库只是长期记忆的一种存储和检索手段。很多记忆完全可以保存在 MySQL 中。

### **3. 第二天如何使用这些记忆？**

假设第二天你重新打开一个新对话：

```
用户：我现在应该先学习什么？
```

系统在调用大模型之前，可能先做一次记忆检索。

```
当前问题：
我现在应该先学习什么？

检索用户记忆：
- 正在开发达人推荐 Agent
- 使用 Java
- 数据源是抖音和小红书
- 正在研究 LangGraph
- 希望深入学习 Agent 技术
```

然后把检索结果放进 Prompt：

```
System:
你是一个技术顾问。

用户长期记忆：
1. 用户正在开发达人推荐 Agent。
2. 用户使用 Java。
3. 用户的数据来自抖音和小红书。
4. 用户希望深入学习 Agent 架构。

当前问题：
我现在应该先学习什么？
```

于是模型就能给出更贴合当前项目的回答。

这就是长期记忆的核心流程：

## **长期记忆的生命周期**

1. **对话产生**
    
    用户不断与大模型交流，产生大量原始消息。
    
2. **记忆提取**
    
    LLM 或规则系统分析对话，提取有价值的信息。
    
3. **记忆存储**
    
    写入 MySQL、Redis、向量数据库等存储系统。
    
4. **记忆召回**
    
    新对话产生时，根据当前问题检索相关记忆。
    
5. **上下文组装**
    
    将相关记忆和当前对话组合成 Prompt。
    
6. **模型推理**
    
    模型利用这些信息生成回答。
    

## **六、第四种记忆：向量检索（Vector Retrieval）**

你可能会问：

历史对话这么多，系统怎么知道应该找哪几条？

这里就涉及 Embedding 和向量数据库了。

### **1. 为什么不能只使用关键词搜索？**

假设历史对话中有这样一段：

```
我想做一个能够自动筛选达人、
分析达人商业价值并生成推荐报告的智能 Agent。
```

现在你问：

```
我之前设计的那个自动找博主的系统，
应该怎么做工具调用？
```

两个问题用词不一样：

- 历史：达人、筛选、商业价值、智能 Agent。
    
- 当前：博主、自动找、工具调用。
    

如果只使用 MySQL LIKE 或关键词搜索，可能找不到真正相关的历史记录。

因此需要语义检索。

### **2. Embedding 是什么？**

Embedding 可以把一段文本转换成一串数字，也就是向量。

例如：

```
文本 A：
我想开发一个达人推荐 Agent。

Embedding：
[0.12, 0.85, 0.32, 0.61, ...]
```

另一段文本：

```
文本 B：
我想做一个自动寻找博主的智能系统。

Embedding：
[0.11, 0.82, 0.35, 0.59, ...]
```

虽然两段话的字面表达不同，但是语义相近，因此它们的向量可能也比较接近。

检索时：

1. 把当前问题转换为向量。
    
2. 到向量数据库中搜索相似向量。
    
3. 获取最相关的历史对话。
    
4. 把历史对话交给大模型。
    

这就是 RAG（Retrieval-Augmented Generation，检索增强生成）在记忆系统中的典型应用。

**语义记忆检索流程**

用户：之前那个达人推荐系统如何调用工具？

**Embedding 模型**

文本 → 向量

**向量数据库**

查找语义最相似的历史记录

**召回结果**

- 正在开发达人推荐 Agent
    
- 曾讨论 Function Calling
    
- 曾讨论 Tool Registry
    

**组装 Prompt → LLM**

这里还有一个关键技术：混合检索（Hybrid Search）。

实际生产环境中，通常可以结合：

- 向量检索：找语义相似内容。
    
- BM25：找关键词匹配内容。
    
- Metadata Filter：按照用户 ID、时间、会话 ID 等过滤。
    

比如用户问某个项目的具体数据库表名，关键词搜索可能比纯向量检索更可靠。

# **七、上下文太长怎么办？记忆压缩（Memory Summarization）**

这是一个非常重要的工程问题。

假设你和大模型聊了 1000 轮。

如果每次都传递 1000 轮完整对话，会产生几个问题：

1. Token 消耗巨大。
    
2. 请求成本增加。
    
3. 推理延迟增加。
    
4. 上下文窗口可能溢出。
    
5. 大量无关历史信息会干扰模型。
    

所以很多系统会采用记忆压缩。

举个例子。

原始对话：

```
第一天：
我想开发达人推荐 Agent。

第二天：
我想使用 Function Calling 实现工具调用。

第三天：
我想使用 LangGraph 实现多步骤工作流。

第四天：
我希望支持多个推荐策略。

第五天：
我希望生成达人推荐报告。
```

系统可以将它们压缩成：

```
用户正在开发一个达人推荐 Agent。

核心需求：
1. 支持多策略达人搜索。
2. 通过 Function Calling 调用业务工具。
3. 使用 LangGraph 管理多步骤工作流。
4. 最终生成达人推荐报告。
```

原来可能需要几千 Token，现在只需要几百 Token。

这里要注意：

**摘要不是原始对话的完整替代品。**

如果后续需要某个具体技术细节，仍然可以回到历史对话数据库中检索原文。

因此，一个比较成熟的记忆系统通常同时保留：

- 原始对话：保证可追溯。
    
- 摘要记忆：快速了解上下文。
    
- 结构化记忆：快速获取稳定事实。
    
- 向量记忆：语义召回相关历史。
    

# **八、把这四种记忆放在一起理解**

|机制|解决什么问题|存储位置|
|---|---|---|
|Context Window|当前对话记住前面说了什么|当前请求上下文|
|Conversation History|找回过去完整聊天|MySQL 等数据库|
|Long-term Memory|记住用户长期信息|MySQL、Redis 等|
|Vector Retrieval|找到语义相关的历史|向量数据库|
|Summarization|压缩过长的历史|数据库、缓存等|

它们不是相互替代的关系，而是相互配合。

# **九、如果让你自己开发一个记忆系统，应该怎么设计？**

结合你正在开发的达人推荐 Agent，我建议你把记忆系统独立设计成一个 Memory Service。

例如：

## **Agent Memory Service 架构**

**Agent Runtime**

接收用户消息、管理 Agent 执行过程

**Memory Service**

**History Manager**

历史对话管理

**Memory Extractor**

记忆提取

**Memory Retriever**

记忆检索

**Summary Manager**

上下文压缩

**MySQL**

对话与事实

**向量库**

语义记忆

**Redis**

短期状态

### **1. 可以设计哪些数据表？**

**user****_****memory：用户长期记忆**

|字段|含义|
|---|---|
|id|主键|
|user_id|用户 ID|
|memory_type|记忆类型|
|content|记忆内容|
|importance|重要程度|
|updated_at|更新时间|

例如：

```
user_id: 1001
memory_type: project
content: 正在开发达人推荐 Agent
importance: 0.95
```

**conversation****_****summary：会话摘要**

|字段|含义|
|---|---|
|id|主键|
|conversation_id|会话 ID|
|summary|对话摘要|
|last_message_id|摘要覆盖到哪条消息|
|updated_at|更新时间|

**message：历史消息**

保存用户、Assistant 和 Tool 的原始消息。

如果需要向量检索，可以额外建立一张 `memory_embedding` 表，保存文本与向量的关联信息。

### **2. 每次用户发消息时的执行流程**

假设用户说：

```
继续帮我设计昨天的达人推荐 Agent。
```

后端执行：

```
1. 接收用户消息
       ↓
2. 获取当前 conversation_id
       ↓
3. 查询最近对话历史
       ↓
4. 检索用户长期记忆
       ↓
5. 检索相关历史对话
       ↓
6. 获取当前会话摘要
       ↓
7. 组装 Prompt
       ↓
8. 调用 LLM
       ↓
9. 保存用户消息和模型回复
       ↓
10. 异步进行记忆提取、摘要更新
```

为什么记忆提取可以异步？

因为用户不需要等记忆提取完成才能拿到回答。可以通过 Kafka 或消息队列，把记忆提取任务交给后台 Worker。

这样不会让记忆管理影响正常对话的响应时间。

# **十、再深入一点：ChatGPT 自己是如何实现记忆的？**

你现在使用的 ChatGPT，可以从三个层次理解：

**第一层：当前对话上下文**

当前聊天中的历史消息可以作为上下文参与后续回答。你在同一个会话里连续追问，我就能结合前面的内容回答。

**第二层：跨会话的历史信息**

系统可以利用之前的聊天历史，提取与当前问题有关的信息，而不需要把所有历史聊天都塞进当前上下文。

**第三层：长期记忆摘要**

系统可以从过去的对话和其他信息来源中提炼相对稳定、值得保留的用户信息，形成记忆摘要。

这三层共同作用，让你感觉 ChatGPT 像一个长期认识你的助手。

但这里需要强调：具体的记忆检索、压缩和调度实现属于产品内部机制，我不能把上面介绍的通用架构说成 ChatGPT 内部的完整源码实现。
