# **五、上下文管理：Agent 系统最重要的工程能力之一**

现在进入实际开发。

假设你开发一个达人推荐 Agent。

用户连续提出这些问题：

```
第 1 轮：
帮我找适合 AI 产品推广的抖音达人。

第 2 轮：
粉丝量要求 50 万以上。

第 3 轮：
只要女性达人。

第 4 轮：
要求近 30 天互动率超过 5%。

第 5 轮：
预算在 10 万以内。

第 6 轮：
把他们按照商业价值排序。
```

你可能会采用最简单的实现方式：

每次请求都把全部历史消息传给模型。

```
messages = [    {"role": "system", "content": system_prompt},    *conversation_history,    {"role": "user", "content": current_question}]response = llm.invoke(messages)
```

这在初期是可以的。

但是当对话变成 100 轮、500 轮呢？

就会出现三个问题：

1. Token 消耗越来越大。
    
2. 历史消息占据上下文空间。
    
3. 模型处理大量无关历史信息，影响效率和准确性。
    

所以，生产级 Agent 通常需要设计上下文管理机制。

## **1. 四种常见的上下文管理方案**

**方案一：完整历史对话（Full History）**

简单

```
messages = [    system_prompt,    *all_history,    current_message]
```

每次都把完整对话发送给模型。

优点：保留原始信息，开发简单。

缺点：Token 越来越多，容易达到上下文上限。

**方案二：滑动窗口（Sliding Window）**

适合短期对话

```
messages = [    system_prompt,    *history[-10:],    current_message]
```

只保留最近 10 轮对话。

优点：控制上下文长度，成本相对稳定。

缺点：较早但重要的信息可能被丢弃。

**方案三：对话摘要（Conversation Summary）**

适合长对话

```
messages = [    system_prompt,    conversation_summary,    *recent_history,    current_message]
```

把之前的对话压缩成摘要，再搭配最近几轮原始消息。

优点：保留重要信息，减少 Token 消耗。

缺点：摘要可能丢失具体数字、条件和细节。

**方案四：长期记忆 + RAG**

复杂 Agent 推荐

```
messages = [    system_prompt,    user_memory,    retrieved_knowledge,    *recent_history,    current_message]
```

把长期记忆、知识库、业务数据放在外部系统，需要时再检索。

优点：不需要把所有历史信息都放入上下文。

缺点：需要设计存储、检索、更新和权限机制。

## **2. 四种方案应该怎么组合？**

实际生产中，我更推荐组合使用，而不是只使用其中一种。

例如：

**用户本轮输入**

**Context Builder（上下文构建器）**

System Prompt

角色、规则

长期记忆

用户偏好

对话摘要

历史重要信息

近期消息

最近 N 轮

RAG / 业务数据检索

当前任务相关的知识、达人数据

**Token Budget Manager**

统计 Token、控制预算、裁剪无关内容

**LLM**

理解问题、推理、决定是否调用工具

这里有两个概念你需要记住：

- Context Builder：负责把本次任务需要的信息组织起来。
    
- Token Budget Manager：负责控制这些信息不能超过模型的 Token 预算。
    

这两个模块可以放在 Agent 的基础设施层，而不是散落在各个业务 Agent 里。
