飞书三个 ID 到底在解决什么问题

一句话：它们是同一个人在不同“圈子”里的三个身份编号。飞书故意设计了三个不同作用域的 ID，用来兼顾隐私、跨应用关联和企业内部管理。

先看一个具体例子。假设张三同时在你们开发者账号下的两个应用里：

┌──────────┬──────────────┬────────────────┐
│          │ 应用 A（OA） │ 应用 B（审批） │
├──────────┼──────────────┼────────────────┤
│ open_id  │ ou_aaa111    │ ou_bbb222      │
├──────────┼──────────────┼────────────────┤
│ union_id │ on_xxx       │ on_xxx         │
├──────────┼──────────────┼────────────────┤
│ user_id  │ 10086        │ 10086          │
└──────────┴──────────────┴────────────────┘

可以看出：

- open_id 每个应用都不一样——换应用就换号；
- union_id 两个应用相同——因为属于同一个开发者；
- user_id 在当前企业内相同——但出了这家企业就不保证唯一。

---
1. open_id：应用内的“工牌号”

作用域：单个应用（一个 app_id）

- 同一个用户，在 OA 应用里是 ou_aaa，在审批应用里可能是 ou_bbb。
- 这是飞书出于隐私考虑的设计：不让不同应用之间随便串联同一个用户。
- 在当前应用内是稳定的，适合做应用内的用户主键。

类比：同一员工在不同子公司的工牌号。在这个子公司内部认这个号，换一家子公司工牌就换了。

什么时候用：你只做一个飞书应用（比如当前的 cp-oa），用它做登录绑定主键完全够用。

---
2. union_id：开发者名下的“统一编号”

作用域：同一个开发者账号下的所有应用

- 同一个用户，只要应用都在你这个开发者账号下，union_id 是一样的。
- 跨应用可以识别出“这是同一个人”。
- 也适合做跨应用统一账号体系的主键。

类比：集团给每个员工发的统一编号，旗下所有子公司通用。

什么时候用：

- 你以后会有多个飞书应用（OA、审批、HR）共用一个账号体系；
- 或者你担心应用被误删重建：重建后 app_id 变了，open_id 会全部变化，但 union_id 不变，可以重新关联。

---
3. user_id：企业租户内的“员工号”

作用域：单个飞书租户（企业）

- 同一个企业内唯一，跨企业不唯一。
- 相对更偏“企业管理”属性，常见于通讯录、组织架构、HR 系统对接。
- 调用飞书通讯录类接口时，user_id 是最常见的参数之一。

类比：公司内部的员工编号。公司内部通用，但拿到别的公司没有任何意义。

什么时候用：

- 同步组织架构、部门、工号；
- 和 HR、通讯录系统对接；
- 不建议作为长期登录主键——它只在当前租户内有效。

---
4. 为什么飞书要设计三个

本质上是三个不同粒度的“唯一性”：

应用内唯一       → open_id   （隐私 + 单应用隔离）
开发者内唯一     → union_id  （跨应用打通）
企业租户内唯一   → user_id   （企业内部管理）

一个 ID 无法同时满足“跨应用识别”“保护隐私”“企业内部管理”这三个目标，所以拆成了三个。
